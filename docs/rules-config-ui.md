# 关键词监控界面（Issue #11，文案随 Issue #87 / #94 更新）

前端通过主工作台的**「监测规则」**按钮打开居中弹窗，不切换路由，因此关闭后不会改变主页面的筛选与浏览上下文（按钮名在 issue #94 由「关键词监控」改为「监测规则」，旁边的入口同时由「AI 语义监控」改为「关注设置」——**只改按钮文字，弹窗自己的标题与内部文案一律不变**，见下节）。页面文案统一使用“关注等级”：红、黄、绿是**关注等级**，不是诊断结论，也不代表病情严重程度。等级可以由关键词规则产生，也可以由 AI 语义判读产生（issue #88）。等级文字必须带「关注」二字，不得只写颜色——**配置界面**（AI 语义监控页的池标题、行内标签、表单等级卡片、筛选下拉）、**工作台列表的行内标签**、**详情抽屉的主等级标签与「关注依据」里的等级标签**都是「红色关注 / 黄色关注 / 绿色关注」（issue #92 统一；issue #94 把详情抽屉里最后一批只写颜色的短词标签也并了过来）。工作台汇总卡与「关注等级」筛选下拉这类紧凑控件仍用「红色」这类短词。抽屉的等级标签下面紧跟一句关注理由，说明这条等级是怎么来的（见「医生看到什么」一节）。

## 文案（Issue #87 规定，不得改写）

下表是**弹窗内部**的文案，issue #94 一律未动（工作台入口按钮是弹窗之外的医生侧文字，
不在此表内）：

| 位置           | 文案                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 页面标题       | `关键词监控`                                                                                   |
| 主描述         | `捕捉报告里写了什么「字」。`                                                                   |
| 辅助描述       | 配置需要关注的疾病名称或关键词，系统会在报告里查找这些字，并把命中的患者按关注等级列到工作台。 |
| 关键词输入提示 | `请输入疾病名称或关键词，例如：溃疡、肿物、癌……`                                               |
| 分工说明       | `关键词监控看「字」 · AI 语义监控看「意思」`                                                   |

**边界（issue #94）**：「不得出现实现词」的扫描只针对**工作台与详情抽屉的渲染文本**，
不扩到管理配置界面——上表这句「看「字」/看「意思」」的分工说明在配置页保留，因为读它的
是配置者，他需要知道两个入口各自在配什么。医生侧的界面里**不得出现** Prompt、提示词、
Semantic Intent、LLM、分类器、JSON Schema 这类实现词：医生要回答的是"这位患者为什么
需要我关注"。（`apps/web/src/RulesModal.test.tsx` 与
`apps/web/src/DetailDrawer.test.tsx` / `Workbench.test.tsx` 各有静态断言兜底。）

## 功能

- 按关键词、关注等级和启停状态筛选，列表采用每页 20 条的服务端分页。
- 新增、编辑和启停规则；编辑与启停请求携带当前 `version`，用于乐观锁校验。
- 可选填写「这个关键词想关注什么情况」（`semanticIntent`，issue #87）：一句话说明
  这条关键词想抓的情况，填写后系统会看命中处的上下文判断这句话是不是真的在说它；
  留空则不判断，命中即计入关注。改动或清空该字段会像改关键词一样生成新版本，
  列表的「关注情况」列对未填写的规则显示「未设置」。
- CSV 批量导入分为预校验和确认写入两个阶段，可下载模板，并展示合法行和错误行。
- 关闭弹窗或编辑面板前检查未保存内容。
- `canManageRules=false` 时隐藏新增和导入入口，列表操作显示为只读。
- 提供加载、空数据、请求失败、保存成功及冲突错误状态。

规则修改只影响后续新数据，不触发历史数据重算（**判读结论同样不重算历史命中**）。
关键词匹配和规则冲突的最终判定均由后端完成。

## 命中结果怎么展示（Issue #87）

判读结论只在**检查详情抽屉**里出现；工作台列表不显示判读理由，只有一行关注理由
（issue #94，见下一节）：

- 所有命中仍全部列出，被判定"未计入关注"的那条**不隐藏**，只是灰底弱化并加
  「未计入关注」标签——关键词命中过是事实，医生要能看见并自己判断；
- 该条下面多一行「结合上下文：报告是否定这个情况（把握高）+ 模型给的理由」；
- 命中标题后的数字仍显示命中总条数，另附「其中 N 条未计入关注」；
- **报告正文/诊断的高亮不再包含被过滤的关键词**：高亮表达的是"这位患者为什么在名单
  上"，而不计入关注的命中恰恰不是这个；
- 工作台列表的「关注理由」列、关键词筛选、汇总计数与推送卡片一律只统计**计入关注**的
  命中，与 `monitor_record.currentLevel` 口径一致；
- 没有 `patientDetail` 权限时，判读的"理由"字段被清空，结论与把握仍在。

## 医生看到什么（Issue #94）

医生侧的三个问题——「为什么这位患者需要我关注」「依据是什么」「哪来的结论」——由两块
界面回答，且**不再出现来源徽标、规则 UUID、规则版本号**（这些数据与 API 契约都保留，
只是退出临床主视线，改由运维与审计路径查看）：

- **工作台列表**把原来的「命中关键词」列换成「关注理由」列，每行一句：
  命中关键等级那一条时写 `命中「腺癌」等 2 处`，只由整份报告读出来时写
  `报告提示需要关注`，两者都有则用「；」连成一句，两条路径都没发现时显示 `—`。
  单元格最大宽度 240px，超出换行不截断。
  关注等级仍显示在「关注等级」列内，**徽标已移除**（所有者决定：医生临床视图完全移除，
  不挪到次级位置）；颜色只表达等级，不承载来源。
- **详情抽屉**顶部是关注等级标签 + 紧随其后的一句关注理由，措辞与列表同一套：有关键词
  命中时点名**当前等级那一条**命中（`报告内容或诊断中发现「腺癌」`），有多条时以
  `等 N 处` 收尾；整份报告读出内容时接上 `报告提示「明确或高度疑似恶性病变」`。
  两句之间用「；」连接，没有可说的依据时不渲染这一行。
- **详情抽屉**把原来的「命中证据」与「AI 语义发现」两个并列区块合并为**一个
  「关注依据」列表**（标题后跟总条数，仍在有关键词命中被过滤时附「其中 N 条未计入关注」）。
  排序是确定的：先按等级（红→黄→绿→未分级），同等级内关键词命中在整份报告发现之前，
  组内保持服务端顺序。两类条目共用等级标签与名称，靠左边框区分（命中青色、报告发现
  中性灰）——分得清，但不是分两段读。
  - 没有任何关键词命中、只因整份报告被读出内容的记录同样落在这个列表里，它解释的就是
    "这条记录为什么在关注列表里"；列表为空时显示「暂无关注依据」。
  - 报告读过了但**没有读出任何内容**时显示「整份报告已核对，未发现需要关注的内容」；
    从未读过（或结论因报告换版而作废）时不显示这句——不会凭空说一句"看过了"。
  - 列表末尾常驻一句「关注等级不是诊断结论，也不代表病情严重程度。」，这里再次出现
    是因为它是**等级**的免责声明，而这一屏就是在解释等级。
- AI **只往上调**等级：关键词路径已经产生的关注等级不会被 AI 降低。
- 证据片段只在「关注依据」里出现一次，**报告正文段落永不被改写**。

这几句都是**确定性措辞**：只用记录上已有的数据（等级、命中关键词、命中位置、依据名称）
拼出来，不调用任何模型，也不新增字段。

## 「关注」二字只有一个来源

等级文字（AI 语义监控页的语义池标题、表格行内标签、筛选下拉选项、新增/编辑表单的等级
单选卡片，详情抽屉的主等级标签与「关注依据」里的等级标签，工作台列表的行内标签，以及
工作台汇总卡与筛选下拉）共用 `apps/web/src/attentionSource.ts` 的 `ATTENTION_LEVEL_LABELS`；
`SemanticMonitorModal.tsx` 只是把它别名成 `POOL_LABELS` 使用。分开写多份字面量正是上一轮
漏改三处的原因，因此**不得**在组件里再声明一份等级中文字面量，改文案只改那一处。
该映射覆盖整个 `MonitorLevelDto`（含「未分级」），所以记录等级可以直接查表，不必判空。

同一文件曾经还导出过 `SOURCE_LABELS` / `SOURCE_TITLES`（来源徽标的文字）。issue #94 移除
临床视图的徽标后，这两个映射没有任何引用点，已一并删除；`attentionSource` 字段本身**仍在
API 契约上**（`docs/api/monitor-api.md`），`attentionReason.ts` 也仍在读它来决定要不要说
「报告提示…」。

改完必须跑 `SemanticMonitorModal.test.tsx` 的渲染文本扫描（扫的是打开新增表单后的
`document.body.textContent`，不是源码）：`/(?:红色|黄色|绿色)(?!关注)/` 不得命中页面
任何位置。这条断言是文案回退的兜底——只改 `attentionSource.ts` 而漏改某个引用点时，
它会失败。

注：`highlight.tsx` 的 `LEVEL_LABELS`（输出「红色」）**不能**合并进来——预警链接 H5
页面复用它并自己拼「关注」二字（`AlertApp.tsx`），改了会渲染成「红色关注关注」。

## API 与配置

界面复用 `docs/rules-api.md` 定义的接口：

- `GET /api/rules`
- `POST /api/rules`
- `PUT /api/rules/{id}`
- `POST /api/rules/import/validate`
- `POST /api/rules/import/confirm`

API 地址读取 `VITE_API_BASE_URL`，未配置时使用 `http://localhost:3000`。请求携带 HttpOnly 会话 Cookie，规则变更的 `actorId` 使用当前登录账号。

“操作日志”按钮当前为禁用提示入口。Issue #31 仅校验是否登录；角色、访问审计和服务端规则写权限仍由 Issue #13 实现，前端只读模式不能替代服务端授权。

## CSV 模板

模板为 UTF-8 CSV，字段如下：

```csv
keyword,level,matchField,matchMode,category,notes
癌,RED,REPORT_TEXT,CONTAINS,,示例规则
```

模板不含 `semanticIntent`：导入的规则一律不做判读（命中即计入关注），需要判读的
规则在界面单条补写。服务端允许的枚举及详细错误格式以 `docs/rules-api.md` 为准。
