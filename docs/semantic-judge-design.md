# AI 语义判读（Validate Match）设计 — issue #87

本文说明"关键词命中之后，让 AI 读一遍上下文再决定这条命中算不算数"这件事是怎么
落地的，以及为什么这样落地。验收口径见 [acceptance.md](./acceptance.md)；数据落库见
[data-dictionary.md](./data-dictionary.md)；规则配置界面见
[rules-config-ui.md](./rules-config-ui.md)。

> **一句话分工**：关键词监控看「字」 · AI 语义监控看「意思」。
> 关键词引擎决定"报告里出现了这些字"，本模块只回答"这句话是不是真的在说医生想
> 关注的那个情况"。它**不诊断、不分级、不改通知、不做闭环**。

## 1. 这套东西解决什么问题，以及不解决什么

**解决**：`未见明显溃疡` 里出现了"溃疡"、`既往胃溃疡病史` 里出现了"胃溃疡"——
关键词引擎按规定必须命中，医生却被这类命中持续打扰，久了就会忽略真正该看的条目。

**不解决，也不允许顺手做**（issue #87 明确列为越界）：

- 不让 AI 判断病情严重程度，不产生红/黄/绿等级；
- 不做报告分类、不接 HIS/EMR、不做历史报告对比与跨次进展分析；
- 不改现有通知体系（个人微信仍是文本消息、企微仍是消息卡片），不新增通知渠道；
- 不删除或覆盖任何原始 `monitor_match` 行。

## 2. 一张图：判读发生在什么位置

```
RIS 报告 ──► 同步任务（apps/worker/src/sync）
                │
                ├─► 关键词匹配引擎（@epgs/matching-engine，纯函数、确定性）
                │        └─► 写入 monitor_match（原始命中，无条件、立即提交）
                │                 │
                │                 └─► 重算 monitor_record.currentLevel
                │
                └─► （同一个 worker 进程，另一个循环）
                        语义判读 SemanticJudgeService
                          └─► 认领一批待判读的 monitor_match
                               └─► @epgs/ai-semantic 调模型 + 校验 + 决策
                                    ├─► 写 monitor_match_semantic（追加审计行）
                                    ├─► 回写 monitor_match 的判读状态列
                                    └─► 重算 monitor_record.currentLevel
```

**判读在命中写入之后，不在匹配内部。** 这是 issue #87 里最要紧的一个顺序问题：

- 命中先由确定性代码无条件产生并提交，AI 只是**事后给这一行加注解**。因此"原始
  关键词命中可审计"不是靠某段代码小心翼翼维护出来的，而是结构上就不可能被破坏——
  判读代码拿不到、也不会去改 `keyword`/`level`/`contextSnippet`/`matchedAt`。
- 反过来（先判读再决定要不要记这一行）会同时违背两条硬要求：没有模型答案就没有
  命中，且模型故障时命中直接消失。任何一次网关抖动都会变成一次静默的监测空白。
- 判读放在同步事务之外，是因为模型调用是一次带秒级超时的网络请求。放进
  `sync-runner.ts` 的事务里，慢模型会拖慢甚至（锁超时）失败本来与它无关的患者
  监测写入。现在的形态是：模型全挂，同步照常，工作台照常，只是详情页少一行
  "上下文判读"，且判读队列会积压——积压是可见的、可补救的，静默丢命中不是。

## 3. 分层：共用的 AI 语义引擎，与它上面的任务

`packages/ai-semantic` 是 #87 与将来的 #88（报告分类）共用的**下层**，#87 只在它上面
实现了 **Validate Match** 一个任务：

| 层             | 位置                                                   | 负责                                                             | 不负责                       |
| -------------- | ------------------------------------------------------ | ---------------------------------------------------------------- | ---------------------------- |
| 结构与契约     | `packages/ai-semantic/src/types.ts`                    | 输入/输出 schema、枚举、版本常量、模型可解释 vs 代码可决策的边界 | 任何 I/O                     |
| 上下文与句子   | `sentence.ts` / `context.ts`                           | 切句、定位锚点句、按预算扩展上下文                               | 取报告正文（由调用方给）     |
| 模型调用       | `model-client.ts` / `openai-compatible-chat-client.ts` | 唯一一次网络调用，超时、重试口径、容错解析                       | 判断模型说了什么对不对       |
| 结构化输出校验 | `parse.ts`                                             | 严格校验字段、枚举取值、长度；不合规即失败                       | 猜测模型想说什么             |
| 证据校验       | `evidence.ts`                                          | 模型引用的片段必须能在**发给它的那段上下文**里定位到             | 放行无法定位的证据           |
| **决策矩阵**   | `disposition.ts`                                       | `filtered: true` 的**唯一**来源                                  | 调用模型、读数据库、看时钟   |
| 任务编排       | `validate-match.ts`                                    | 串起来 + 每步的 fail-open 出口 + 审计字段                        | 落库、记日志、抛异常         |
| 数据库与循环   | `apps/worker/src/semantic/`                            | 认领队列、写审计、回写状态、重算等级、日志                       | 判断（全部来自上面的纯函数） |
| 对外接口与界面 | `apps/api`、`apps/web`                                 | 展示"未计入关注"与判读理由，脱敏                                 | 重算等级、改变筛选口径       |

这个分层是照着 `@epgs/matching-engine` 的既有约定做的：**包内不碰框架、不碰数据库、
不记日志、不发网络请求**（模型客户端是注入的接口），所以整个判读逻辑可以脱离
Postgres 和真实模型做单测——`packages/ai-semantic` 的 142 个测试全部不联网。

**为什么模型客户端零依赖**：医院自有网关是否 OpenAI 兼容尚未确认。
`SemanticModelClient` 是接口，`OpenAiCompatibleChatClient` 是唯一实现（用 Node 内置
`fetch`，不引入 SDK），`SEMANTIC_MODEL_API_STYLE` 是留给第二种风格的接缝。落地前先跑
`pnpm --filter worker run semantic:probe` 验通。

## 4. 模型输出与"模型不决策"

模型被要求只输出一个 JSON 对象：

```json
{
  "matched": true,
  "semantic_status": "PRESENT",
  "reason": "报告明确描述该病变存在。",
  "evidence": "胃窦见巨大溃疡",
  "confidence": "HIGH",
  "intent_excludes_history": false
}
```

| 字段                      | 取值                                                  | 含义                                     |
| ------------------------- | ----------------------------------------------------- | ---------------------------------------- |
| `matched`                 | boolean                                               | 这段话是否表达规则关注的情况             |
| `semantic_status`         | `PRESENT` `NEGATED` `SUSPECTED` `HISTORY` `UNCERTAIN` | 报告里那句话属于哪一类                   |
| `reason`                  | ≤300 字符                                             | 给医生看的解释句                         |
| `evidence`                | 原文片段                                              | 模型据以判断的那几个字（会被回原文校验） |
| `confidence`              | `HIGH` `MEDIUM` `LOW`                                 | 把握程度                                 |
| `intent_excludes_history` | boolean                                               | 医生写的"关注情况"是否明确排除了既往史   |

**模型不决定过不过滤，也从不被问到"要不要过滤"。** 它只提供对文本的判断，最终
`filtered` 由 `disposition.ts` 的纯函数按下面这张表给出：

| 判读结论                                            | 处理           | 理由                                                                                |
| --------------------------------------------------- | -------------- | ----------------------------------------------------------------------------------- |
| `PRESENT`                                           | 保留           | 报告写了，就是命中                                                                  |
| `SUSPECTED`                                         | 保留           | "考虑…可能""不能除外"是医生在提可能性，正是要盯的人；把"也许"当"没有"是最危险的过滤 |
| `NEGATED` + `HIGH`                                  | **未计入关注** | "未见明显溃疡"，本 issue 要消灭的典型误报                                           |
| `NEGATED` + `MEDIUM`/`LOW`                          | 保留           | 否定还拿不准，正是误过滤最可能发生的时候                                            |
| `HISTORY` + `HIGH` + 关注情况排除既往史             | **未计入关注** | 医生自己说了不看既往史                                                              |
| `HISTORY` + `HIGH` + 关注情况未排除既往史           | 保留           | 关注情况没提既往史 ≠ 允许丢弃既往史命中                                             |
| `HISTORY` + `MEDIUM`/`LOW`                          | 保留           | 同上                                                                                |
| `UNCERTAIN`                                         | 保留           | 读不懂不等于没有                                                                    |
| 自相矛盾（如 `NEGATED` 却 `matched=true`）          | 保留           | 两个字段有一个是错的，无法判断哪个错，只能不采信                                    |
| 任何失败（超时/报错/JSON 非法/证据对不上/无上下文） | 保留           | 见下一节                                                                            |

**没有任何一格的默认方向是"过滤"。** 矩阵里能产生 `filtered: true` 的分支只有两条，
且都要求 `HIGH` 把握。

## 5. 失败一定回到原始关键词结论（fail-open）

这是本模块的安全底线：**AI 永远不能成为患者监测的单点故障**。

| 失败情形                              | 结果                                                       |
| ------------------------------------- | ---------------------------------------------------------- |
| 判读功能关闭 / 模型未配置             | 不调用模型，命中全部计入关注（与 #87 之前完全一致）        |
| 规则没写"关注情况"                    | 不调用模型，不写审计行，命中计入关注，队列照常清空         |
| 模型超时 / 连接失败 / HTTP 错误       | 记一条 `outcome=ERROR` 审计行，保留命中，按退避重试        |
| 模型返回非法 JSON / 缺字段 / 枚举越界 | 同上（失败原因是 `INVALID_RESPONSE`/`SCHEMA_*`）           |
| 模型给的证据在原文里定位不到          | **整条结论作废**，保留命中（理由见下）                     |
| 同一命中连续失败到上限                | 终止重试、保留命中、写终态时间戳，坏行不会无限消耗模型调用 |
| 判读过程中抛出的任何意外              | 被循环兜住并记日志；不会让 worker 退出，同步与推送不受影响 |

"证据定位不到就作废整条结论"是刻意的：这句话的**依据**找不到，我们就无法判断它的
**结论**是否也错。诚实的记录是"调用成功了，但答案没法核对"，而不是"用一个打了折的
结论继续”。

多条命中、同一关键词多次出现、正则命中、精确匹配、同一报告命中多个字段——都走同一条
路径：每条命中独立判读、独立决策、独立留痕，一条失败不影响其他条。

## 6. 上下文怎么取

- **必须包含命中所在的那一整句**；可以扩展到前后句或本章节；
- **不允许默认整篇报告**；
- 预算 `SEMANTIC_CONTEXT_CHAR_BUDGET`（默认 400 字符）；同一关键词在同段里多次出现时，
  把各次出现所在的句子一起带上，避免模型看到半句话就下结论；
- 句子切不出来（没有标点、超长、锚点定位不到）→ 按"上下文不足"处理，保留命中。

取的是 `monitor_record` 里已经受权限保护的报告字段，只存在于内存中，
**不落库、不进日志**（见下节）。

## 7. 审计与隐私

每次判读**调用**写一行 `monitor_match_semantic`（含失败行），记录：任务与版本、
用的哪个模型、输入/上下文/证据的哈希、证据与上下文在原文中的偏移、耗时、机器码形式的
错误、决策结果与决策依据。字段级定义见 [data-dictionary.md](./data-dictionary.md#monitor_match_semantic--上下文判读审计issue-87)。

**不落库的内容**：报告原文、Prompt、上下文片段、模型原始响应、`evidence` 原文。
要复核"当时到底发了什么"，用偏移量 + `monitor_record` 自己的报告正文重新算——
报告正文本来就有 `patientDetail` 权限门，等于让审计复用同一道门，而不是新开一道。

**唯一的自由文本是 `reason`**（模型给医生看的解释句），因此它：长度上限 300 字符；
调用方没有 `patientDetail` 权限时置空；模型的原始响应与错误响应体绝不入库、绝不打日志
（它们可能把报告原文回显出来）。残留风险已有记录：模型仍可能在 `reason` 里复述报告
片段，这一点已知、已评估，未做逐字脱敏。

**日志约束**：只记数量、ID、机器码（模型/决策/错误）和耗时。不记患者姓名、报告正文、
上下文片段、`reason`。CI 有静态门禁（`log-sanitization.spec.ts`）兜底。

## 8. 配置与开关

全部在 `apps/worker`，见 [apps/worker/.env.example](../apps/worker/.env.example)。
默认 **关闭**：`SEMANTIC_JUDGE_ENABLED=false` 时 worker 不会联系任何模型，行为与
#87 之前逐字一致。

模型变量（`SEMANTIC_MODEL_BASE_URL`/`SEMANTIC_MODEL_API_KEY`/`SEMANTIC_MODEL_NAME`）
**刻意不设为"启用时必填"**。这个进程同时跑患者监测的同步任务，因为一个可选 AI 层
配置不全而拒绝启动，等于让 AI 成为全系统的单点故障——这正是 #87 禁止的。缺配置时
判读自我禁用并打一条错误日志，同步照常。格式与取值范围仍然在启动时严格校验，
写错了会在启动时大声失败。

| 变量                              | 默认          | 说明                                     |
| --------------------------------- | ------------- | ---------------------------------------- |
| `SEMANTIC_JUDGE_ENABLED`          | `false`       | 总开关                                   |
| `SEMANTIC_MODEL_API_STYLE`        | `openai-chat` | 网关风格接缝，目前只实现这一种           |
| `SEMANTIC_MODEL_TIMEOUT_MS`       | `10000`       | 单次调用上限                             |
| `SEMANTIC_MODEL_MAX_TOKENS`       | `512`         | 回复长度上限                             |
| `SEMANTIC_CONTEXT_CHAR_BUDGET`    | `400`         | 上下文预算                               |
| `SEMANTIC_JUDGE_INTERVAL_SECONDS` | `30`          | 循环周期                                 |
| `SEMANTIC_JUDGE_BATCH_SIZE`       | `10`          | 每轮判读条数（避免饿死同进程的同步任务） |
| `SEMANTIC_JUDGE_MAX_ATTEMPTS`     | `3`           | 失败重试上限，到顶即终态保留             |
| `SEMANTIC_JUDGE_LEASE_SECONDS`    | `300`         | 认领租约，须大于 batchSize × timeout     |

## 9. 怎么手工验证（上线前）

> **界面名称随 issue #94 变了**：下面第 1、4 步说的「上下文判读」行现在是
> **「结合上下文」**，「命中证据」区块已与「AI 语义发现」合并为**「关注依据」**。
> 判据本身（被过滤的命中仍列出、灰底 + 「未计入关注」、结论 + 把握 + 理由、正文高亮
> 不含它）逐条不变。详见 [rules-config-ui.md](./rules-config-ui.md) 的「医生看到什么」。

1. **不接模型**：`SEMANTIC_JUDGE_ENABLED=false` 启动 worker，工作台行为与改动前一致，
   详情页没有"上下文判读"行——这条先确认，它是回滚基线。
2. **验通网关**：填好模型变量后 `pnpm --filter worker run semantic:probe`。
   它只发合成的非患者文本，用来确认 base url / 名称 / 鉴权是否可用。
3. **小批量试跑**：`pnpm --filter worker run semantic:once` 手动跑一轮并打印统计
   （认领 / 判读成功 / 失败 / 跳过）。观察 `monitor_match_semantic` 的
   `decision_reason` 分布是否符合预期。
4. **看详情页**：被过滤的命中仍列在"命中证据"里，灰底 + 「未计入关注」+ 一行
   「上下文判读」（结论 + 把握 + 理由）；报告正文高亮里**不再**包含它。
5. **拔线演练**：把 `SEMANTIC_MODEL_BASE_URL` 改成一个不可达地址，确认工作台列表、
   红黄绿、通知推送全部照常，只有详情页判读行缺失——这是 fail-open 的验收动作。

## 10. 与 #88 的关系

`packages/ai-semantic` 从第一天就按"#87 + #88 共用下层"设计：模型客户端、结构化输出
校验、超时/重试、失败隔离、证据校验、模型与版本审计、任务与 Prompt 版本、输入哈希、
耗时日志都已就位，`SemanticTask` 枚举留了扩展位。**#88（报告分类）本轮没有实现**，
本轮也没有为它预留任何"半成品"代码路径——扩到 #88 需要新增一个任务模块与一个枚举值，
不需要改动本模块的任何判读逻辑。
